### IMPL-12: The overview's initial thread delivery must not depend on a scheduling race

**Source:** `docs/impl-guides/operator-findings-20260805-2235-impl-guide-20260805-2242-verify-report-20260806-0042.md#IV-02`
**Source:** `docs/audits/operator-findings-20260805-2235.md#OP-08`
**Severity/Priority:** ⚠️ medium
**Workstream:** A — the comment layer, prototype and template together
**Reasoning tier:** high

#### Context
`loadThreads()` reads `this.setThreads` **before** awaiting the store:

```js
this.setThreads(await this.store.list());   // proto-comments.js:622
```

The property lookup happens at call time, before the promise resolves, so a page that patches
`setThreads` after `init()` returns — which is exactly what `comments.html:288-294` does in `wire()`
— is bypassed for that first delivery. In production the page survives only because Firebase's
`subscribe()` fires a second delivery that *does* go through the patched method. Drive the layer
through the documented `options.store` seam with a store whose `list()` resolves and whose
`subscribe()` does not immediately re-deliver, and the page sits on "Se încarcă firele de discuție…"
with zero cards.

The post-`wire` fallback at `comments.html:333` is the other half: it re-renders only
`if (Array.isArray(layer.threads) && layer.threads.length)`, and it calls `render` without calling
`hydrate`, so even when it fires the bodies stay on "Se încarcă textul…".

#### What to do
1. In `proto-comments.js`, split the line so the method is resolved at call time, after the await.
   Do the same in `templates/proto-comments.js`.
2. In `comments.html` and `templates/comments.html`, make the post-`wire` catch-up unconditional and
   run the same pair the patched `setThreads` runs — render *and* hydrate — so a delivery that
   arrived before wiring is fully reflected rather than half-reflected.
3. Check the other `setThreads` call sites in `proto-comments.js` (`:665`, `:974`) for the same
   read-before-await shape.

#### Scope
- Files: `proto-comments.js`, `comments.html`, `<skill>/templates/proto-comments.js`,
  `<skill>/templates/comments.html`
- New files: none

#### Definition of Done
- [ ] With an injected store via `protoComments.init({store})` whose `list()` resolves and whose
      `subscribe()` delivers nothing, `comments.html` renders one `.cm-thread` per thread and the
      loading message is hidden
- [ ] Message bodies hydrate on that same path — no card left reading "Se încarcă textul…"
- [ ] The live Firebase path is unchanged: signed in on localhost, the page still lists every thread
- [ ] `templates/proto-comments.js` and `templates/comments.html` carry the same two fixes
- [ ] Skill suite still 139/139

#### Edge cases
- The subscribe delivery arriving *before* `wire()` completes: the unconditional catch-up must not
  double-render or double-hydrate (the `hydrating` map guards the second, `replaceChildren` the
  first — confirm both).
- An empty thread list: the catch-up must show the empty state, not leave the loading message up.
  This is precisely what the current `&& layer.threads.length` guard gets wrong.

#### Test scenarios
- **Integration:** inject a store, count `.cm-thread` — must equal the store's thread count.
- **Integration:** inject an empty store — `#cm-empty` visible, `#cm-loading` hidden.

#### Dependencies
- Blocked by: none
- Blocks: nothing

### IMPL-14: An unresolvable anchor must render the fallback sentence, not a link to nowhere

**Source:** `docs/impl-guides/operator-findings-20260805-2235-impl-guide-20260805-2242-verify-report-20260806-0042.md#IV-05`
**Severity/Priority:** ⚠️ medium
**Workstream:** A — the comment layer, prototype and template together
**Reasoning tier:** high

#### Context
`safeLink()` is written as a `try/catch` around the link builder, on the assumption that an
unresolvable anchor throws. It does not. `deepLink()` deliberately falls back to
`new URL(pageName() + carried, root)` when `navigableUrl()` refuses the stored value
(`proto-comments.js:935-936`) — a fallback that is correct on a *screen*, where "the page being
viewed" is the thread's own page. On the overview, `pageName()` is `comments.html`, so a thread
whose `anchor.page` is `https://evil.example.com/x.html` renders a confident, live-looking link to
`comments.html#c=…`. The `else` branch at `comments.html:240-245` — the sentence that says the link
could not be built — is unreachable dead code.

#### What to do
1. In the overview's link helper (both copies), decide the link is valid only when the produced
   filename matches what `anchor.page` actually claimed; return null on a mismatch so the existing
   fallback sentence renders.
2. Do not change `deepLink()`'s own fallback. It is correct for its caller on a screen, and
   `IMPL-16`/`IMPL-17` rely on that reading; the wrong behaviour is the overview trusting it.
3. Keep the `try/catch` — it is still the right guard for a thread with no anchor at all.

#### Scope
- Files: `comments.html`, `<skill>/templates/comments.html`
- New files: none

#### Definition of Done
- [ ] A thread with `anchor.page = 'https://evil.example.com/x.html'` renders the "Legătura nu se
      poate construi · Link could not be built" sentence and no `<a>`

- [ ] A thread with no `anchor` at all does not throw and renders the fallback sentence
- [ ] `templates/comments.html` behaves identically

#### Edge cases

### IMPL-15: Overlapping hydrate batches must not permanently replace `history.replaceState`

**Source:** `docs/impl-guides/operator-findings-20260805-2235-impl-guide-20260805-2242-verify-report-20260806-0042.md#IV-08`
**Severity/Priority:** ⚠️ medium
**Workstream:** A — the comment layer, prototype and template together
**Reasoning tier:** high

#### Context
`hydrate()` (`comments.html:267-286`) neutralises `layer.needsRestore` and `history.replaceState`
for the duration of a batch and restores them in `.finally()`. It captures the "originals" at the
top of each call, so a second batch starting while the first is in flight captures the **stub** as
its original and restores that. `history.replaceState` is then permanently `function () {}` for the
lifetime of the page. Reproduced: `String(history.replaceState)` after a second subscribe delivery
returns the stub.

Two batches overlapping is not exotic — it is what a `list()` delivery followed by a `subscribe()`
delivery does, which is the ordinary path.

The same function leaks `hydrating[id]`: entries are set before the batch and never deleted, so a
thread whose detail fetch fails is never retried, even on a later delivery that would have succeeded.

#### What to do
1. Replace the save/restore pair with an in-flight counter: patch on the 0→1 transition, restore on
   1→0, keeping one reference to the genuine originals rather than one per call.
2. Delete the `hydrating` entry in the per-thread `catch`, so a failed detail can be retried by a
   later delivery. Leave it set on success — the `messages` array is then the guard.
3. Port both to `templates/comments.html`.

#### Scope
- Files: `comments.html`, `<skill>/templates/comments.html`
- New files: none

#### Definition of Done
- [ ] After two deliberately overlapping hydrate batches, `String(history.replaceState)` is the
      native function, not a stub — and `history.replaceState` still works on the page afterwards
- [ ] `layer.needsRestore` is likewise the layer's own method after both batches settle
- [ ] A thread whose detail fetch rejects is re-attempted on the next delivery
- [ ] `templates/comments.html` carries both fixes

#### Edge cases
- A batch that throws synchronously before `Promise.all` — the counter must still unwind.
- A third batch starting while two are in flight: the counter, not a boolean, is what makes this
  correct.

#### Test scenarios
- **Integration:** injected store; trigger two deliveries back to back; read
  `String(history.replaceState)` and assert it is native.
- **Integration:** injected store whose `loadThreadDetail` rejects once then resolves; assert the
  body renders after the second delivery.

#### Dependencies
- Blocked by: none
- Blocks: nothing

3. Check `safePageName()` and `needsRestore()` (`proto-comments.js:228-231`, `:944-951`) for the same

### IMPL-17: A thread with no page must stop flapping the store's `orphaned` flag

**Source:** `docs/impl-guides/operator-findings-20260805-2235-impl-guide-20260805-2242-verify-report-20260806-0042.md#IV-10`
**Severity/Priority:** ⚠️ low
**Workstream:** A — the comment layer, prototype and template together
**Reasoning tier:** high

#### Context
`belongsToThisPage()` returns `true` for a thread with no `anchor.page`
(`proto-comments.js:694-696`), so such a thread reaches `elementFor()` on *every* page. Its selector
resolves on the page it was written on and fails everywhere else, so `renderThreads()` writes
`orphaned: true` on one page and `orphaned: false` on the next — the flag flaps as the reviewer
navigates, which is the exact failure page-scoping was introduced to prevent.

**Keep the render behaviour, fix the write.** The `true` return is deliberate and load-bearing: it
mirrors `deepLink()`'s own `anchor.page || pageName()` fallback and `safePageName()`'s falsy guard
(`proto-comments.js:223-231`), so a legacy thread stays reachable and its deep link still resolves.
Treating a missing page as belonging to *no* page would make those three disagree and would silently
strand every thread stored before the field existed. What is not deliberate is claiming to know that
another page's markup broke.

#### What to do
1. Skip the `privateOrphanUpdate` call — in both directions — when `anchor.page` is absent. Keep the
   thread rendering exactly as it does now.
2. Say why in a comment: the layer cannot establish orphanhood for a thread it cannot locate to a
   page, which is the same argument the block at `proto-comments.js:673-691` already makes about
   another page's markup.
